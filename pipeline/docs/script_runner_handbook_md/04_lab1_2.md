## Lab 1: write the team source contract and run bronze

**Goal.** Write, by hand, the ODCS 3.1 contract that describes the `teams.csv` file as it arrives, upload it, and run `bronze:team`. The step must fail loudly if the file does not match your contract.

**Why this is the first contract.** A source contract is the front door. It promises only the **shape** of what arrives: which columns exist and that the file is not empty. It says nothing about whether the values are valid, because by design nothing is validated before silver. That separation is the point: if bronze judged values, one bad value could stop the load, and you could never replay from the original.

The file you are describing has this header:

```
team_id,team_name,city,league,founded_year,home_park,payroll_cap_musd,mascot
```

### Step 1: write the contract

Create `student/contracts/fbl_source_team.yaml`. Fill in every `<...>`. The comments say what each part is for and what reads it.

```yaml
apiVersion: v3.1.0          # which ODCS version this file follows
kind: DataContract          # always this for a contract
id: fbl.source.team         # <dataProduct>.<layer>.<name>. It must match dataProduct and layer below
name: <a readable name>
version: 1.0.0              # semantic version: bump it whenever behaviour changes
status: active              # draft | active | deprecated
domain: baseball_operations
dataProduct: fbl            # groups contracts; the runner runs one product at a time
description:
  purpose: <one sentence: what does this contract promise?>
  limitations: <what it does NOT promise>
  usage: <how the file may be used>
customProperties:           # ODCS's extension point: anything the standard has no field for
  - property: layer
    value: source           # source | silver | gold | semantic: decides which stage reads this contract
  - property: owner
    value: <who is accountable for this file>
schema:
  - name: fbl_team                  # the logical table name
    physicalName: bronze.fbl_team   # schema.table the bronze step will write
    logicalType: object
    physicalType: table
    customProperties:
      - property: entity            # the short key the runner uses: bronze:team, silver:team
        value: team
      - property: landingFolder     # the folder under the landing directory that holds the file
        value: <folder name>
    quality:
      - metric: rowCount            # an ODCS library metric
        mustBeGreaterThan: 0
        type: library
        severity: error
        description: <what this check protects>
    properties:                     # one entry per column the file must contain
      - name: team_id
        logicalType: string         # source columns are ALWAYS string: typing is silver's job
        physicalType: STRING
        required: true              # here required means: the COLUMN must be present in the file
        description: <what the column holds>
      # add the other seven columns, in the order of the header above
```

**What each block does, and why it is there**

| Block | Who reads it | Why |
| --- | --- | --- |
| `id`, `dataProduct`, layer in `customProperties` | Lint and the planner | The id must be `<dataProduct>.<layer>.<name>`; the layer decides which stage uses the file |
| `version`, `status` | The registry | Every run records which version governed it |
| `customProperties.owner` | Lint (required) | A contract with no accountable owner is documentation nobody maintains |
| `schema[0].customProperties.entity` | The planner | The key that links source, silver and gold contracts for the same thing |
| `landingFolder` | The bronze step | Tells it where to read; the contract, not the code, knows the folder |
| `physicalName` | Bronze and the schema check | The table to write, and the table to verify afterwards |
| `quality` with `rowCount` | The schema check | An empty file is a structural failure |
| `properties` | Bronze | The columns that must be present. This is the promise |

### Step 2: check it on your computer

```bash
python tools/contract_tool.py --contracts student/contracts lint
python tools/contract_tool.py compare --mine student/contracts
```
Expected lint line when your file is right: `1 contracts, 0 errors, 0 warnings`. The `compare` output will say `== fbl.source.team: matches the reference` and `not written yet` for the contracts you have not written. Any difference it lists is a place to look: not necessarily a mistake, but a choice you made that the reference did not.

The compare tool and lint are your safety net while you learn: lint checks that the contract agrees with itself, compare shows how it differs from the answer key.

### Step 3: upload and run

Upload your YAML to `/Volumes/mlb_dev/governance/pipeline/contracts/`. Run the Job with `steps` = `bronze:team` (leave `contracts_dir` at its default, your folder). Expected log:

```
run <id> | catalog mlb_dev | 1 of 1 steps selected
[setup] ok
published 1 contracts (1 new/changed); compiled 0 rules
[contracts] ok
[bronze:team] start
bronze.fbl_team: 15 rows  [contract fbl.source.team v1.0.0]
[bronze:team] ok
run <id>: 0 rows rejected, 0 auto-corrections, 0 failed rules, 0 broken contract checks, 0 failed steps
PIPELINE OK
```

**What happened inside.** The runner read your YAML, linted it, recorded it in `governance.data_contracts` and `data_contracts_history`, then asked the planner what to run. The bronze step read `teams/` as text, compared the header with your `properties`, wrote `bronze.fbl_team` with three lineage columns, and finally compared the written table with your contract. Nothing about team files is hard-coded in the bronze script: it only knows how to follow a source contract.

### Step 5: break it on purpose

Each drill below was run on the real code; the messages are exactly what you should see.

| Drill | What to change | What you see |
| --- | --- | --- |
| Misspell a column in your contract | Change `payroll_cap_musd` to `payroll_cap_usd`, re-upload, rerun | `[bronze:team] FAILED: Data quality failure: team BRZ-001 (1): Expected columns are present (missing: payroll_cap_usd)`, and the run ends with `PIPELINE FAILED (DQFailure)` |
| Forget `landingFolder` | Delete that property | Lint stops the run before any data is touched: `fbl.source.team: source schema needs customProperties.landingFolder` |
| The file is empty | Upload a `teams.csv` with only the header line | `team BRZ-002 (1): Source file is not empty` |
| The folder is missing | Rename the `teams` folder in the Volume | `landing folder not found: .../teams. Upload the file there (the contract says landingFolder = teams).` |

After each, look at `governance.pipeline_step_log`: the failed step is recorded, and the report was still written to `reports/`. Put everything back before moving on.

**Reflect.** (1) Why must source properties all be `string`? (Typing is silver's job; a typed source contract would let a bad value fail or silently change at load.) (2) Where is the knowledge of the folder name, and why is it good that it is not in the code? (3) Which of the four drills did lint catch, and which did only the run catch? What does that tell you about what lint can and cannot see?

## Lab 2: write the team silver contract and run silver

**Goal.** Describe, in a second contract, what a *clean* team looks like: real types, standard forms, the key, and every rule that decides whether a row is accepted, repaired or rejected. Then run `silver:team` and read what happened to each of the 15 rows.

**Why this contract does more than the last one.** In Lab 1 the contract only listed columns. A silver contract is where your **quality policy** lives. The silver script has no knowledge of teams at all: it generates its typing SQL from this contract's properties, and applies the rules listed in its `quality` section. Change the contract and you change the behaviour, with no code edit. That is what makes one engine usable for thousands of tables.

### Step 1: write the contract

Create `student/contracts/fbl_silver_team.yaml`. The header follows Lab 1, with these differences:

- `id: fbl.silver.team`, layer `silver`, and a root-level custom property `dependsOn` with value `fbl.source.team`. This is the lineage link: lint checks the source contract exists and that every column you read from it is really there.
- `physicalName: silver.fbl_team`, `entity: team`.
- No `landingFolder`; silver reads the bronze table.

**Properties.** One per column, now with real types. Four settings are new:

| Property setting | What it does |
| --- | --- |
| `logicalType: integer` / `number` / `date` / `string` | The silver typing SQL casts to this type with `try_cast`, so a bad value becomes NULL instead of crashing the job |
| `required: true` | Lint demands a `not_null` rule that covers this column. A promise nothing enforces is rejected at lint time |
| `primaryKey: true` with `primaryKeyPosition: 1` | Lint demands a uniqueness rule for the key |
| a `customProperties` entry `standardize` = `upper` or `initcap` | The typing SQL applies that function after trimming, and a `standardized` rule logs every value it changed |

Use these types and settings:

| Column | Type | Required | Key | Standardize |
| --- | --- | --- | --- | --- |
| team_id | string | yes | position 1 | upper |
| team_name | string | yes | | |
| city | string | yes | | |
| league | string | yes | | initcap |
| founded_year | integer | yes | | |
| home_park | string | yes | | |
| payroll_cap_musd | number | yes | | |
| mascot | string | **no** | | |

The property syntax looks like this (shown for `league`; write the others yourself):

```yaml
    properties:
      - name: league
        logicalType: string
        physicalType: STRING
        required: true
        description: 'League: North or South.'
        customProperties:
          - property: standardize
            value: initcap
```

**Quality rules.** Each rule is one entry under `quality`, in this shape:

```yaml
    quality:
      - name: TEAM-004                 # the rule id; unique across ALL contracts
        type: custom
        engine: fbl-dq-engine          # ODCS's way to carry a rule only one engine understands
        dimension: conformity
        severity: error
        description: League must be North or South
        implementation:
          rule_type: allowed_values    # how a violation is detected
          columns: [league]
          expression: "'North','South'"
          action: quarantine           # what happens to a violating row
          owner: Baseball Operations
```

Write all eight:

| Rule | `rule_type` | Columns | Expression | `action` | Plain meaning |
| --- | --- | --- | --- | --- | --- |
| TEAM-001 | `exact_duplicate` | `*` | (none) | `dedupe` | An identical repeated row is dropped (nothing is lost) |
| TEAM-002 | `unique_strict` | `team_id` | (none) | `quarantine` | A key that repeats with different content is rejected, every copy |
| TEAM-003 | `not_null` | all required columns | (none) | `quarantine` | Required values must be present |
| TEAM-004 | `allowed_values` | `league` | `'North','South'` | `quarantine` | League must be a known value |
| TEAM-005 | `range` | `founded_year` | `2000 AND year(current_date())` | `quarantine` | Founded between 2000 and this year |
| TEAM-006 | `custom` | `payroll_cap_musd` | `payroll_cap_musd > 0` | `quarantine` | Business rule: the cap must be positive |
| TEAM-007 | `standardized` | `league` | (none) | `standardize` | Log values the cleaning re-cased |
| TEAM-008 | `standardized` | `team_id` | (none) | `standardize` | Log values the cleaning trimmed or upper-cased |

The four actions are the four things a quality system can do with a bad row: **repair** (`dedupe`, `standardize`: the row is fixed, kept and logged), **reject** (`quarantine`: removed from silver, returned with the reason), **tolerate** (`warn`: kept and logged), **halt** (`fail`: stop the run). Choosing the action for each rule is the real design work.

### Step 2: see the SQL your contract will generate

Before running anything, print the typing SELECT the silver step will execute:

```bash
python tools/contract_tool.py --contracts student/contracts typed-sql team
```
You will see lines like:

```sql
upper(NULLIF(trim(`team_id`), ''))                 AS `team_id`,
initcap(NULLIF(trim(`league`), ''))                AS `league`,
try_cast(NULLIF(trim(`founded_year`), '') AS INT)  AS `founded_year`,
...
to_json(struct(t.`team_id`, t.`team_name`, ...)) AS _raw,
```

| Piece | Why |
| --- | --- |
| `trim` | Whitespace is the commonest reason two keys that look equal do not join |
| `NULLIF(..., '')` | One representation of missing (NULL), so every rule has one thing to test |
| `upper` / `initcap` | The `standardize` setting from your contract |
| `try_cast(... AS INT)` | The type from your contract; a value like `N/A` becomes NULL and is rejected by the not-null rule, not a crash |
| `_raw` | The **original text** of the row as JSON, so a rejected row goes back to its owner exactly as it was sent |

Compare with what you wrote: every line is derived from a property of your contract.

### Step 3: check, upload, run

```bash
python tools/contract_tool.py --contracts student/contracts lint
python tools/contract_tool.py compare --mine student/contracts
```
Upload `fbl_silver_team.yaml` to the Volume's `contracts/` folder. Run the Job with `steps` = `bronze:team,silver:team` and `fail_on_rejects` = `false` (so a run with rejected rows finishes green while you learn). Expected log:

```
published 2 contracts (2 new/changed); compiled 8 rules
silver.fbl_team: in=15 deduped=1 rejected=6 out=8  [contract fbl.silver.team v1.0.0]
run <id>: 6 rows rejected, 3 auto-corrections, 0 failed rules, 0 broken contract checks, 0 failed steps
PIPELINE OK
```
**Row accounting:** 15 in, minus 1 duplicate, minus 6 rejected, equals 8 out. For every table, `rows_in - rows_deduped - rows_rejected = rows_out`. If that ever fails, the engine itself has a defect.

### Step 4: read what happened to each row

```sql
SELECT rule_ids, disposition, payload
FROM mlb_dev.governance.dq_quarantine WHERE run_id = '<your run id>' ORDER BY row_id;

SELECT rule_id, action, violations FROM mlb_dev.governance.dq_rule_results
WHERE run_id = '<your run id>' AND layer = 'silver' AND violations > 0 ORDER BY rule_id;
```
You should find, among the quarantine rows:

| Team | Rule | Disposition | Why |
| --- | --- | --- | --- |
| T05 | TEAM-001 | auto_corrected | An identical duplicate row was dropped |
| T06 | TEAM-007 | auto_corrected | League typed `south` was re-cased to `South` |
| T09 (two rows) | TEAM-002 | rejected | Same key, different founding year: nobody can say which is right |
| T10 | TEAM-003 | rejected | Blank team name |
| T11 | TEAM-005 | rejected | Founded 2099 |
| T12 | TEAM-004 | rejected | League `XX` (also logged by TEAM-007 as re-cased to `Xx`, which is harmless) |
| T13 | TEAM-006 | rejected | Negative payroll cap |

Each rejected row's `payload` is the record as the source sent it, which is what you would send back to the file's owner.

### Step 5: break it on purpose

| Drill | Change | What you see | The lesson |
| --- | --- | --- | --- |
| **A change that fails nothing** | Delete the `standardize: initcap` setting from `league` | Nothing fails. The result becomes `in=15 deduped=1 rejected=7 out=7`: T06's `south` is no longer re-cased, so TEAM-004 now rejects it | A check cannot know your *intent*. Only counts you expect, or golden tests, notice this |
| **A contract that disagrees with itself** | Remove `league` from TEAM-003's `columns` | Lint: `fbl.silver.team: property league is required but no not_null/no_nulls rule covers it` | Lint guards consistency between what you promise and what you enforce |
| **A typo across contracts** | In the silver contract rename a property so it no longer matches a source column | Lint: `property <name>: source column '<name>' not in fbl.source.team` | Lint cross-checks contracts against each other before any data is read |
| **Soften a rule** | Change TEAM-006's `action` to `warn` and bump `version` to `1.1.0` | T13 stays in silver and is only logged as a warning: one fewer rejected row, one more row out | Policy is a line in a contract. The version records that it changed |

**Reflect.** (1) Why do `required` and `primaryKey` force lint to demand rules? (2) Which action would you give a negative payroll cap, a missing mascot, and a team listed twice with different data, and why? (3) What did the quarantine give you that a deleted row would not?
