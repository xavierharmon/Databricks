## Lab 0: set up Databricks and prove the launcher works

**Goal.** Run the runner in `--plan-only` mode from a Databricks Job, reading the reference contracts from a Volume. No data is touched. If this works, the plumbing is proven and every later lab only adds contracts.

**Why start here.** Almost every first-run failure in a script pipeline is plumbing (a wrong path, a missing library, a Job set up differently from what you expected), not logic. A plan-only run exercises all of that, and nothing else, so when it fails you know it is plumbing.

### Step 1: build the kit on your computer

```bash
cd mlb-lakehouse
python tools/build_runner_kit.py
```
This creates `dist/runner_kit/` with two folders and a map:

- `pipeline_volume/` goes into the code Volume: the launcher, `code/lakehouse.zip`, an empty `contracts/` folder for your own YAML, `contracts_reference/` (the answer key), `transforms/gold/`, and `definitions/`.
- `data_volume/` goes into the data Volume: the three CSV files under `fbl/`.
- `UPLOAD_MAP.md` lists every file and its destination.

**What happens inside.** The builder zips the `lakehouse` and `lib` packages into one `lakehouse.zip`. A zip is used because a Volume upload screen is slow with many small files, and Python can import straight from a zip on its search path. This is the same shape a CI job would build and publish automatically later.

### Step 2: create the schemas and Volumes (SQL editor, by hand)

```sql
CREATE SCHEMA IF NOT EXISTS mlb_dev.governance;
CREATE SCHEMA IF NOT EXISTS mlb_dev.bronze;
CREATE VOLUME IF NOT EXISTS mlb_dev.governance.pipeline COMMENT 'pipeline code, contracts, transforms';
CREATE VOLUME IF NOT EXISTS mlb_dev.bronze.landing COMMENT 'landed source files and run reports';
```
**Why by hand.** The runner creates every table it needs, but it cannot create the place it is itself stored in. These four statements are the whole bootstrap.

**Why two Volumes.** Code and data have different owners, permissions and lifetimes. In a real estate a data engineer should be able to land files without being able to overwrite the pipeline code.

**Check:** `SHOW VOLUMES IN mlb_dev.governance;` and `SHOW VOLUMES IN mlb_dev.bronze;` each list one Volume.

### Step 3: upload

In Catalog Explorer open each Volume, create the folders, and use **Upload to this volume** (keep the file names).

| From `dist/runner_kit/` | To |
| --- | --- |
| `pipeline_volume/run_pipeline.py` | `/Volumes/mlb_dev/governance/pipeline/run_pipeline.py` |
| `pipeline_volume/code/lakehouse.zip` | `/Volumes/mlb_dev/governance/pipeline/code/lakehouse.zip` |
| `pipeline_volume/contracts_reference/` (every YAML, keeping its `source`, `silver`, `gold`, `semantic` subfolders) | `/Volumes/mlb_dev/governance/pipeline/contracts_reference/` |
| `pipeline_volume/transforms/gold/*.sql` | `/Volumes/mlb_dev/governance/pipeline/transforms/gold/` |
| `pipeline_volume/definitions/*.sql` | `/Volumes/mlb_dev/governance/pipeline/definitions/` |
| `data_volume/fbl/teams/teams.csv`, `players/players.csv`, `batting/batting.csv` | `/Volumes/mlb_dev/bronze/landing/fbl/teams/`, `players/`, `batting/` |

Also create an empty folder `/Volumes/mlb_dev/governance/pipeline/contracts/` now. It is where your own contracts will go.

**Check:**
```sql
LIST '/Volumes/mlb_dev/governance/pipeline/';
LIST '/Volumes/mlb_dev/governance/pipeline/code/';
LIST '/Volumes/mlb_dev/bronze/landing/fbl/teams/';
```
You should see `run_pipeline.py`, `lakehouse.zip` and `teams.csv`.

### Step 4: create the Job

In Jobs and Pipelines choose Create job, add one task, and set:

| Field | Value |
| --- | --- |
| Task name | `run_pipeline` |
| Type | Python script |
| Source | the option for a script in a Volume or cloud storage (the docs call it DBFS/S3) |
| Path | `/Volumes/mlb_dev/governance/pipeline/run_pipeline.py` (if rejected, try `dbfs:/Volumes/mlb_dev/governance/pipeline/run_pipeline.py`) |
| Compute | Serverless |
| Environment | Base environment version 5 if offered (its documented library list includes PyYAML 6.0.2) |
| Parameters | the JSON list below |

```json
["--catalog", "mlb_dev",
 "--pipeline-root", "/Volumes/mlb_dev/governance/pipeline",
 "--data-root", "/Volumes/mlb_dev/bronze/landing",
 "--run-id", "{{job.run_id}}",
 "--contracts-dir", "{{job.parameters.contracts_dir}}",
 "--steps", "{{job.parameters.steps}}",
 "--stages", "{{job.parameters.stages}}",
 "--entities", "{{job.parameters.entities}}",
 "--plan-only", "{{job.parameters.plan_only}}",
 "--fail-on-rejects", "{{job.parameters.fail_on_rejects}}"]
```
Then add these **Job parameters** (the Job-level settings, separate from the task):

| Name | Default | Meaning |
| --- | --- | --- |
| `contracts_dir` | `/Volumes/mlb_dev/governance/pipeline/contracts` | Which contracts to run with |
| `steps` | `all` | Explicit steps such as `silver:team,gold-publish`, or `all` |
| `stages` | `all` | A comma list of `bronze`, `silver`, `gold`, `semantic`, or `all` |
| `entities` | `all` | Limit to some entities, or `all` |
| `plan_only` | `false` | `true` prints the plan and stops |
| `fail_on_rejects` | `true` | `true` ends the run in failure when rows were rejected |

**What happens inside, and why it is built this way.** The task parameters are a fixed list of strings that Databricks hands to the script as command-line arguments. The `{{job.parameters.x}}` references let you change a setting per run ("Run now with different parameters") without editing the task. Job parameters cannot be left unset, which is why `all` means "no filter". The launcher is deliberately tiny: it adds `code/lakehouse.zip` to Python's import path and calls the runner. All the real behaviour lives in the zip, so the launcher never changes when the pipeline does.

### Step 5: run it twice

**Run A: expect a clean refusal.** Run the Job with the defaults but set `plan_only` to `true`. Your `contracts` folder is still empty, so the runner stops with:
```
no contract YAML files found in /Volumes/mlb_dev/governance/pipeline/contracts
```
That is the runner refusing to guess. A pipeline that quietly did nothing here would be worse than one that fails.

**Run B: the real smoke test.** Run with different parameters: `plan_only` = `true` and `contracts_dir` = `/Volumes/mlb_dev/governance/pipeline/contracts_reference`. Open the run, then the task's output or logs. Expected (shortened; the full plan has 15 numbered lines):
```
PLAN for product 'fbl' (contracts from /Volumes/mlb_dev/governance/pipeline/contracts_reference)
  0. setup               create schemas, governance tables and views
  1. contracts           lint every contract, record the versions, compile the rules
  2. bronze:batting
       read the batting files as text; require the columns promised by fbl.source.batting v1.0.0; not empty; write bronze.fbl_batting
  ...
  5. silver:team          after bronze:team
       type and clean the bronze rows (SQL generated from fbl.silver.team v1.0.0); apply 8 rules; clean rows -> silver.fbl_team, rejects -> governance.dq_quarantine
  7. silver:player        after bronze:player, silver:team
  ...
  11. gold-publish        after gold:dim_player, gold:dim_team, gold:fact_batting
  14. report              summarise the run; fail it if rows were rejected or a contract is broken
```
Read the plan: nobody wrote this order down. It was derived from the contracts, so `silver:player` comes after `silver:team` because the player contract has a foreign key to team.

### If it does not work

| What you see | Likely cause | What to do |
| --- | --- | --- |
| The task type or Volume source is not offered | Your workspace or plan may not allow Python script tasks | Use the fallback below |
| The path is rejected or the file is not found | The Volume path form differs | Try the `dbfs:/Volumes/...` form; re-check the upload with `LIST` |
| `cannot find the pipeline code` | The launcher cannot see `lakehouse.zip` | Check `code/lakehouse.zip` exists under the pipeline root; the launcher looks in `<pipeline-root>/code` |
| `No module named 'yaml'` | The environment has no PyYAML | Select base environment 5, or add `pyyaml` under the task's dependent libraries |
| `contracts folder not found` | Wrong `contracts_dir` | It must be a Volume folder path exactly as uploaded |

**Fallback if script tasks are unavailable.** Create a notebook with one cell that runs the same launcher, and keep everything else in this guide unchanged:

```python
runpy.run_path("/Volumes/mlb_dev/governance/pipeline/run_pipeline.py", run_name="__main__")
```
