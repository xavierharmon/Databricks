## Lab 3: write the gold contract and transform, and see write, audit, publish

**Goal.** Describe the published `dim_team` table in a third contract, write its transformation as a SQL file, and run `gold:dim_team` and `gold-publish`. Then prove that bad data cannot reach the published table.

**Why gold works differently from silver.** Silver *filters*: a bad row is set aside and the good rows carry on. Gold is the published product, so its rules are *assertions*: a violation means the whole table is untrustworthy and the right response is to stop. That is why every gold rule must use `action: fail`, and why lint refuses anything else.

Gold also never writes straight into the published table. The step builds the table in a staging schema (`gold_stage`), audits it there, and only a separate step, `gold-publish`, copies it into `gold`. This is **write, audit, publish**. Without it, a failed assertion would leave the freshly overwritten bad table live until someone fixed it. With it, the published table is untouched whenever an audit fails.

### Step 1: write the contract

Create `student/contracts/fbl_gold_dim_team.yaml`. Start from your silver contract and change:

| Setting | Value | Why |
| --- | --- | --- |
| `id`, layer | `fbl.gold.dim_team`, `gold` | The id pattern is `<product>.<layer>.<name>` |
| root `customProperties` `dependsOn` | `fbl.silver.team` | Lineage, and the planner builds gold after silver |
| `slaProperties` | `freshness`, value `24`, unit `h`, element `dim_team` | A promise to consumers that the semantic layer later checks |
| schema `name`, `physicalName` | `dim_team`, `gold.fbl_dim_team` | The published table. The staged copy is derived from it |
| schema `customProperties` | `entity: dim_team`, `reconcilesTo: silver.fbl_team` | `reconcilesTo` names the silver table whose row count gold must equal |
| every property | `required: true`, including `mascot` | A gold guarantee is that nothing is NULL. The transform labels a missing mascot |
| `team_id` | `primaryKey: true`, `primaryKeyPosition: 1` | Lint will demand a uniqueness rule |

Use the same eight columns and types as your silver contract. Under `quality` write the library `rowCount` check and two rules, both with `action: fail`:

```yaml
      - name: GLD-001
        type: custom
        engine: fbl-dq-engine
        dimension: completeness
        severity: error
        description: 'Gold guarantee: no NULL in any dim_team column'
        implementation:
          rule_type: no_nulls
          columns: '*'
          action: fail
          owner: Data Engineering
```

| Rule | `rule_type` | Columns | `action` | Meaning |
| --- | --- | --- | --- | --- |
| GLD-001 | `no_nulls` | `*` | `fail` | No NULL anywhere in the table |
| GLD-004 | `unique` | `team_id` | `fail` | One row per team: the table's grain |

You only write these two. The step adds a third check itself: **reconciliation**, comparing the staged row count with the silver table named in `reconcilesTo`.

### Step 2: write the transform

Create `transforms/gold/dim_team.sql` and upload it to `/Volumes/mlb_dev/governance/pipeline/transforms/gold/` (replacing the kit's copy):

```sql
SELECT team_id, team_name, city, league, founded_year, home_park, payroll_cap_musd,
       coalesce(mascot, 'None') AS mascot
FROM silver.fbl_team
```
**Why a SQL file and not code.** The contract points at the transformation (by convention `transforms/gold/<entity>.sql`, or an explicit `transformSql` property), and the gold script just runs it. The SQL never mentions rules or contracts: it reads only clean silver and shapes it. Keeping them apart means an analytics engineer can change a transform without touching the quality policy, and the other way round.

**Why `'None'` and not NULL.** A report grouped by mascot should show a group called None, not silently lose rows with a missing mascot. Only optional descriptive text is defaulted. A numeric measure is never defaulted: a missing number is rejected in silver instead, because a made-up zero would corrupt every average.

## Lab 4: scale the pattern with player, then batting

**Goal.** Add the other two entities by writing six more contracts and two more transforms, and watch the pipeline grow without a single code change. By the end you have the whole FBL pipeline, built from your own contracts.

**Why this lab matters most.** Everything so far could have been one hand-written script. What makes the design valuable is what happens now: the runner, the stage scripts and the engine do not change at all. The only new input is contracts, and the plan, the order, the rules and the checks all follow. With thousands of tables, adding a table is writing contracts, not writing code.

### Part A: player

Write three contracts and one transform, following the pattern of Labs 1 to 3:

- `student/contracts/fbl_source_player.yaml` (id `fbl.source.player`, `landingFolder: players`, entity `player`)
- `student/contracts/fbl_silver_player.yaml` (id `fbl.silver.player`, `dependsOn: fbl.source.player`)
- `student/contracts/fbl_gold_dim_player.yaml` (id `fbl.gold.dim_player`, `dependsOn: fbl.silver.player`)
- `transforms/gold/dim_player.sql`

The source file header is `player_id,first_name,last_name,birth_date,bats,throws,team_id,position,height_in,weight_lb,nickname`.

**Silver properties**

| Column | Type | Required | Notes |
| --- | --- | --- | --- |
| player_id | string | yes | primary key, `standardize: upper` |
| first_name, last_name | string | yes | |
| birth_date | date | yes | `classification: personal` (a property setting for sensitive data) |
| bats, throws | string | yes | `standardize: upper` |
| team_id | string | yes | `standardize: upper`, **foreign key to team** |
| position | string | yes | `standardize: upper` |
| height_in, weight_lb | integer | yes | |
| nickname | string | **no** | optional |

**New idea: the foreign key.** A relationship is how a contract says "this column points at another table's key". It is written on the property:

```yaml
      - name: team_id
        logicalType: string
        physicalType: STRING
        required: true
        relationships:
          - to: fbl_team.team_id      # the other contract's schema name, then its column
            type: foreignKey
        customProperties:
          - property: standardize
            value: upper
```
Two things now depend on it. **Lint** insists on a matching `referential` rule (PLR-010), and the **planner** uses it to decide that `silver:player` must run after `silver:team`. Neither you nor the code ever writes that order down.

**Silver rules (11)**

| Rule | `rule_type` | Columns | Expression | `action` | Plain meaning |
| --- | --- | --- | --- | --- | --- |
| PLR-001 | `exact_duplicate` | `*` | (none) | `dedupe` | Identical duplicate rows are removed |
| PLR-002 | `unique_strict` | player_id | (none) | `quarantine` | A key repeated with different content is rejected, every copy |
| PLR-003 | `not_null` | all required columns | (none) | `quarantine` | Required fields must be present |
| PLR-004 | `allowed_values` | bats | `'L','R','B'` | `quarantine` | Bats must be L, R or B |
| PLR-005 | `allowed_values` | throws | `'L','R'` | `quarantine` | Throws must be L or R |
| PLR-006 | `allowed_values` | position | `'P','C','1B','2B','3B','SS','LF','CF','RF','DH'` | `quarantine` | A valid position code |
| PLR-007 | `range` | height_in | `60 AND 84` | `quarantine` | Height between 60 and 84 inches |
| PLR-008 | `range` | weight_lb | `120 AND 350` | `warn` | Odd weights are logged, the row is kept |
| PLR-009 | `custom` | birth_date | `months_between(current_date(), birth_date) >= 16 * 12` | `quarantine` | A player must be at least 16 (also catches future dates) |
| PLR-010 | `referential` | team_id | `silver.fbl_team.team_id` | `quarantine` | The team must exist in clean silver |
| PLR-011 | `standardized` | bats | (none) | `standardize` | Log values the cleaning re-cased |

**Gold `dim_player`.** Same pattern as `dim_team`: all columns required, plus a derived `full_name` (string); a foreign key from `team_id` to `dim_team.team_id`; entity `dim_player`, `reconcilesTo: silver.fbl_player`. Rules, all `fail`: GLD-002 (`no_nulls`, `*`), GLD-005 (`unique`, player_id), GLD-009 (`referential`, team_id, expression `gold.fbl_dim_team.team_id`). The transform:

```sql
SELECT player_id, first_name, last_name, concat(first_name, ' ', last_name) AS full_name, birth_date, bats, throws,
       team_id, position, height_in, weight_lb, coalesce(nickname, 'None') AS nickname
FROM silver.fbl_player
```

**Look at the plan before you run:**
```bash
python tools/contract_tool.py --contracts student/contracts plan
```
```
 1. bronze:player
 2. bronze:team
 3. silver:team               after bronze:team
 4. gold:dim_team             after silver:team
 5. silver:player             after bronze:player, silver:team
 6. gold:dim_player           after gold:dim_team, silver:player
 7. gold-publish              after gold:dim_player, gold:dim_team
```
Nobody ordered this. Lines 5 and 6 appeared because of your foreign keys. Upload the contracts and run the Job with `steps` = `all`, `entities` = `team,player` and `fail_on_rejects` = `false`. Expected:

| Table | In | Deduped | Rejected | Out |
| --- | --- | --- | --- | --- |
| silver team | 15 | 1 | 6 | 8 |
| silver player | 42 | 1 | 10 | 31 |
| gold dim_team / dim_player | | | | 8 / 31 |

**The cascade.** Ten players are rejected, and one of them, P040, had perfectly valid data. His `team_id` is T09, and T09 was rejected in silver team. Query it:
```sql
SELECT rule_ids, payload FROM mlb_dev.governance.dq_quarantine
WHERE run_id = '<your run id>' AND source_table = 'player' AND disposition = 'rejected' ORDER BY row_id;
```
The cause of P040's rejection is two tables upstream, which is exactly why the order matters: the player rule checks references against the *clean* team table.

**Break it**

| Drill | Change | What you see |
| --- | --- | --- |
| Hide the foreign key | Delete the `relationships` block from `team_id` in the silver player contract | Lint: `a referential rule checks team_id against silver.fbl_team (fbl.silver.team) but property team_id declares no foreignKey relationship to fbl_team. Add one: the runner derives the build order from relationships` |
| Keep the key, drop the rule | Remove rule PLR-010 only | Lint: `property team_id has a foreignKey relationship but no referential rule` |

The first of these used to slip through: without the relationship the plan listed `silver:player` before `silver:team`, and the run failed in the middle with `PLR-010 checks references against silver.fbl_team, which does not exist`. It was caught while preparing this lab, and lint now stops it before anything runs.

### Part B: batting

Write `fbl_source_batting.yaml` (`landingFolder: batting`, entity `batting`), `fbl_silver_batting.yaml`, `fbl_gold_fact_batting.yaml` and `transforms/gold/fact_batting.sql`. The source header is `player_id,season,team_id,g,ab,h,doubles,triples,hr,rbi,bb,so,sb`.

What is new here:

- **A composite key.** `player_id`, `season` and `team_id` together identify a row: set `primaryKey: true` on all three with `primaryKeyPosition` 1, 2, 3. Lint then needs one uniqueness rule over all three columns.
- **Two foreign keys:** `player_id` to `fbl_player.player_id` and `team_id` to `fbl_team.team_id`.
- **Business rules** that compare columns with each other.
- **A fact table:** gold stores additive columns only. Ratios such as batting average are not stored, because an average of averages is wrong; they belong in the metric view (Lab 5).

**Silver properties.** `player_id` (string, upper, key 1, FK player), `season` (integer, key 2), `team_id` (string, upper, key 3, FK team), and `g`, `ab`, `h`, `doubles`, `triples`, `hr`, `rbi`, `bb`, `so`, `sb` as required integers.

**Silver rules (12)**

| Rule | `rule_type` | Columns | Expression | `action` | Plain meaning |
| --- | --- | --- | --- | --- | --- |
| BAT-001 | `exact_duplicate` | `*` | (none) | `dedupe` | Identical repeated rows are removed |
| BAT-002 | `unique_strict` | player_id, season, team_id | (none) | `quarantine` | One line per player, season, team |
| BAT-003 | `not_null` | all required columns | (none) | `quarantine` | Required values must be present (text like `N/A` becomes NULL and lands here) |
| BAT-004 | `range` | season | `2008 AND year(current_date())` | `quarantine` | A season the league existed |
| BAT-005 | `range` | g | `0 AND 162` | `quarantine` | Games played between 0 and 162 |
| BAT-006 | `custom` | h | `h <= ab` | `quarantine` | Hits cannot exceed at bats |
| BAT-007 | `custom` | hr | `hr <= h` | `quarantine` | Home runs cannot exceed hits |
| BAT-008 | `custom` | h | `doubles + triples + hr <= h` | `quarantine` | Extra-base hits cannot exceed hits |
| BAT-009 | `custom` | ab | `ab <= g * 6` | `quarantine` | No more than 6 at bats a game |
| BAT-010 | `custom` | ab | `ab >= 0 AND h >= 0 AND doubles >= 0 AND triples >= 0 AND hr >= 0 AND rbi >= 0 AND bb >= 0 AND so >= 0 AND sb >= 0` | `quarantine` | Counting stats cannot be negative |
| BAT-011 | `referential` | player_id | `silver.fbl_player.player_id` | `quarantine` | The player must exist in clean silver |
| BAT-012 | `referential` | team_id | `silver.fbl_team.team_id` | `quarantine` | The team must exist in clean silver |

**Gold `fact_batting`.** All columns required, plus derived `singles`, `total_bases` and `plate_appearances_approx` (integers); the same three-column key; foreign keys to `dim_player.player_id` and `dim_team.team_id`; entity `fact_batting`, `reconcilesTo: silver.fbl_batting`, `dependsOn: fbl.silver.batting`. Rules, all `fail`: GLD-003 (`no_nulls`), GLD-006 (`unique` over the three columns), GLD-007 and GLD-008 (`referential` to the two gold dimensions), GLD-010 (`custom`: `h <= ab AND hr <= h AND ab <= g * 6`, which re-checks the arithmetic after the transform ran). The transform:

```sql
SELECT player_id, season, team_id, g, ab, h, doubles, triples, hr, rbi, bb, so, sb,
       h - doubles - triples - hr           AS singles,
       h + doubles + 2 * triples + 3 * hr   AS total_bases,
       ab + bb                              AS plate_appearances_approx
FROM silver.fbl_batting
```

| silver player | 42 | 1 | 10 | 31 |
