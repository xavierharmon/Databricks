## Lab 5 (optional): write a semantic contract for a metric view

**Goal.** Put a contract around a metric view, so that anyone querying it can rely on its fields, its measures and what the numbers mean. This lab needs a workspace that supports metric views; if creating one fails, note the error and skip to Lab 6.

**Why semantic contracts differ.** A table's contract can be checked by comparing columns. A metric view can change its *meaning* while every column keeps its name: edit one formula and every dashboard changes silently. A semantic contract therefore promises four things, each enforced differently:

| Promise | Enforced by |
| --- | --- |
| **Interface**: every field and measure exists and returns the promised type | A real `MEASURE()` query for each one |
| **Meaning**: the formulas have not changed without notice | A fingerprint (`exprHash`) of each formula; lint recomputes it from the SQL |
| **Behaviour**: the numbers are right | `reconcile` (equals a direct query on gold), `expect` (known values), `bounds` (value ranges) tests |
| **Service**: the data is fresh and its last gate was clean | A freshness promise checked against the gold build record |

### Step 1: write the contract for `mv_fbl_roster`

The metric view definition is already in your Volume (`definitions/mv_fbl_roster.sql`): five fields (team_name, league, position, batting_hand, throwing_hand) and five measures (players, avg_height_in, avg_weight_lb, switch_hitters, teams). Create `student/contracts/fbl_semantic_mv_fbl_roster.yaml` with:

- `id: fbl.semantic.mv_fbl_roster`, layer `semantic`, a freshness SLA of 24 h.
- schema `name: mv_fbl_roster`, `physicalName: semantic.mv_fbl_roster`, `physicalType: view`.
- schema `customProperties`: `definition` = `sql/fbl/metric_views/mv_fbl_roster.sql` (lint uses the file name), `dependsOn` = `[gold.fbl_dim_player, gold.fbl_dim_team]`, and `consumers` (who uses it; documentation for now).
- one property per field and per measure, each with `customProperties` of `kind` (`field` or `measure`) and `exprHash`.

```yaml
      - name: avg_height_in
        logicalType: number
        required: false
        description: Average height in inches.
        customProperties:
          - property: kind
            value: measure
          - property: exprHash
            value: '000000000000'      # a placeholder: the tool computes the real one
```
**You cannot compute a fingerprint by hand, and you should not try.** Write the placeholder, then run `python tools/contract_tool.py --contracts student/contracts stamp` and the tool fills in every `exprHash` from the SQL. Types: counts (`players`, `switch_hitters`, `teams`) are `integer`; averages are `number`; fields are `string`.

Add two tests under `quality` (the rest of the reference's tests follow the same shapes):

```yaml
      - name: SEM-FBLR-001
        type: custom
        engine: fbl-semantic-checks
        dimension: accuracy
        severity: error
        description: Players per team equals the player dimension counts.
        implementation:
          test_type: reconcile
          dimensions: [team_name]
          measures: [players]
          tolerance: 0
          compare_sql: "SELECT t.team_name, COUNT(*) AS players FROM gold.fbl_dim_player p JOIN gold.fbl_dim_team t ON p.team_id = t.team_id GROUP BY t.team_name"
      - name: SEM-FBLR-002
        type: custom
        engine: fbl-semantic-checks
        dimension: accuracy
        severity: error
        description: Average height is plausible for every team and position.
        implementation:
          test_type: bounds
          dimensions: [team_name, position]
          bounds:
            avg_height_in: [60, 84]
```
**Why a `reconcile` test.** It asks the metric view and the gold table the same question independently and compares the answers group by group. If the view's join or formula is wrong, the two disagree. It holds whatever the data is, which is why it suits data you keep editing. Fixed `expect` values suit historical data that never changes.

### Step 2: check, upload, run

```bash
python tools/contract_tool.py --contracts student/contracts stamp
python tools/contract_tool.py --contracts student/contracts lint
```
Upload the contract. Run `steps` = `all` first so gold is published, then `steps` = `semantic:mv_fbl_roster`. Expected log lines (the check count may differ a little in your workspace):
```
created mlb_dev.semantic.mv_fbl_roster
fbl.semantic.mv_fbl_roster v1.0.0: 28 checks, 0 broken
```
**What happened inside.** The step created the view from its SQL, then ran a `MEASURE()` query for every field and measure you declared, checking each returned type. It then ran your tests and the freshness check. Type mismatches are only warnings until the contract sets `strictTypes: true`, because the exact types Databricks returns for metric view columns were not confirmed; read any warnings from your first run and then switch it on.

### Step 3: break it on purpose

| Drill | Change | What you see |
| --- | --- | --- |
| **A silent change of meaning** | In `mv_fbl_roster.sql` change `AVG(height_in)` to `MAX(height_in)` and upload only the SQL | Lint stops the run: `fbl.semantic.mv_fbl_roster: avg_height_in: definition changed (hash ... != contract ...). Bump the contract version ... and run contract_tool.py stamp` |
| **A wrong expectation** | Set the bounds to `[100, 120]` | The semantic step fails with a bounds test naming how many groups were out of range |
| **A measure that is not there** | Rename `players` in the contract only | Lint: the measure is in the contract but not in the metric view definition |

**Reflect.** (1) Why is a formula change breaking even when no column name changes? (2) What does `stamp` record, and what does it deliberately not decide? (3) Which of the four promises would a changed join key violate?

## Lab 6: run the whole pipeline as one Job

**Goal.** Run everything from one Job, learn the knobs (steps, stages, entities, run parameters), read the evidence, and set up a schedule and an alert.

**Why one Job and one runner call.** The runner holds the order and the failure policy. A Job's job is only to supply parameters, a schedule, and a notification. Keeping those separate means you can change *when and how it runs* without touching *what it does*, and run exactly the same command on your laptop.

### Step 1: a full run that is meant to fail

Run with all defaults, so `fail_on_rejects` is `true`, `steps` is `all`. The Job ends **failed**, and that is the pipeline working: 46 rows were rejected and the run refuses to end green. The last lines of the log read:

```
PIPELINE FAILED (DQFailure): KICK BACK: run <id>: 46 rows rejected, ...
```
Open the run: every task before it succeeded, the gold tables are published, and the evidence is complete. That failure is the alert.

### Step 2: read the evidence in order

```sql
SELECT step, status, detail FROM mlb_dev.governance.pipeline_step_log WHERE run_id = '<id>' ORDER BY started_at;   -- what ran, in what order
SELECT * FROM mlb_dev.governance.v_dq_summary;                          -- rows in / deduped / rejected / out
SELECT * FROM mlb_dev.governance.v_dq_open_rejects;                     -- the kick-back list, with the original records
SELECT * FROM mlb_dev.governance.v_contract_failures;                   -- any broken or warned contract checks
```
The HTML report for the run is at `/Volumes/mlb_dev/bronze/landing/reports/pipeline_report_<id>.html`. Download it from the Volume and open it in a browser.

### Step 3: use the knobs

Use "Run now with different parameters":

| You want | Set |
| --- | --- |
| Only bronze and silver | `stages` = `bronze,silver` |
| One entity through every layer | `entities` = `player` (the gold publish step is included for the layers selected) |
| Exactly these steps | `steps` = `silver:team,silver:player` |
| A report-only run (do not fail on rejects) | `fail_on_rejects` = `false` |
| See the plan without running anything | `plan_only` = `true` |

Try `steps` = `silver:player` alone, after a full run. It still works because the team table it checks references against already exists. Now delete the silver team table and run it again: `PLR-010 checks references against silver.fbl_team, which does not exist: run its silver step first`. The step checks its own prerequisites rather than failing deep inside Spark.

### Step 4: schedule and alert

- **Schedule.** In the Job, add a schedule (a cron expression) set for after the source files are due. The source contracts promise arrival by 06:00 UTC, so schedule it later. A file-arrival trigger on the landing folder is the alternative; the docs list `file_arrival` as a trigger type, and I have not tried it with these Volumes.
- **Alert.** Add a failure notification (email) to the Job. Because rejected rows end the run in failure, one setting alerts you to *both* a broken step and a data problem. A second option is a SQL alert on `SELECT COUNT(*) FROM mlb_dev.governance.v_dq_open_rejects`.
- **Concurrency.** Set the maximum concurrent runs to 1. The pipeline rebuilds tables, so two runs at once would corrupt each other.
- **Retries.** Leave retries off while learning. A data-quality failure is deterministic, so a retry only repeats it and delays the alert.

**Reflect.** (1) Why does the Job fail even though every step succeeded? (2) What is the difference between `fail_on_rejects = false` and a stage failing? (3) Which parameter would you change to rerun just the batting slice after the source owner corrects the file?
