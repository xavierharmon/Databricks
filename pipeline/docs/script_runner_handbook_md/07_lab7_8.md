## Lab 7: failure drills and safe contract changes

**Goal.** Learn which mechanism catches which mistake, then practise changing a contract the way you will in a team: edit, version, check, publish, enforce.

**Why drills.** You asked that the scripts fail if you miss something. That only works if you know what each check can and cannot see. Lint reads files. The engine reads data. The live schema check compares a contract with a real table. The diff gate compares two versions of a contract. Each is blind to what the others see, so you need all four.

### Part A: which check speaks up

Every row below was produced by running the exact change on the real code.

| Mistake | Caught by | Message | When |
| --- | --- | --- | --- |
| Forgot `landingFolder` | Lint | `fbl.source.team: source schema needs customProperties.landingFolder` | Before any data is read |
| A column name differs between source and silver contracts | Lint | `fbl.silver.team: property payroll_cap_musd: source column 'payroll_cap_musd' not in fbl.source.team` | Before any data is read |
| A column is required but no rule enforces it | Lint | `property league is required but no not_null/no_nulls rule covers it` | Before any data is read |
| A rule points at another table but no foreign key is declared | Lint | `a referential rule checks team_id against silver.fbl_team ... declares no foreignKey relationship ... Add one` | Before any data is read |
| The file is missing a promised column | Bronze | `team BRZ-001 (1): Expected columns are present (missing: payroll_cap_usd)` | At run time, step stops |
| The file is empty | Bronze | `team BRZ-002 (1): Source file is not empty` | At run time, step stops |
| Bad data slips into silver | Gold audit | `dim_team GLD-001 (1): Gold guarantee: no NULL in any dim_team column` | The run stops; the published table is untouched |
| The gold contract promises a type the table lacks | Gold schema check | `Contract broken: fbl.gold.dim_team column types match (founded_year is int, contract says string)` | Before publish |
| The gold transform file is missing | The gold step | `transform SQL not found: .../transforms/gold/dim_team.sql ...` | At run time |
| A rule was removed or weakened by mistake | **Nothing fails** | Counts change (for example 7 rejected instead of 6) | You notice only if you know what to expect |

The last row is the most important lesson. **Checks verify that your pipeline agrees with your contracts. They cannot verify that your contracts say what you meant.** The defence is expected counts (the answer-key numbers), golden values in semantic contracts, and a human reviewing contract changes in a pull request.

### Part B: change a contract the safe way

Every change follows the same loop. Do each of the next two exercises in full.

**Exercise 1: reject the 900 lb player.** Rule `PLR-008` only warns about weights outside 120 to 350, so player P027 (900 lb) reaches gold. Promote it:

1. In `fbl_silver_player.yaml` change the rule's `action` from `warn` to `quarantine` (and its `severity` to `error`), and raise `version` from `1.0.0` to `1.1.0`.
2. `python tools/contract_tool.py --contracts student/contracts lint`
3. Upload the file, run the Job with `steps` = `all` and `fail_on_rejects` = `false`.
4. Expected: silver player 42 in, 1 deduped, **11** rejected, **30** out. Silver batting rejects **32**, out **51**, because P027's two batting lines now cascade. Gold: 8 / **30** / **51**. Total rejected: 49.
5. Check the history: `SELECT contract_id, version, loaded_at FROM mlb_dev.governance.data_contracts_history WHERE contract_id = 'fbl.silver.player' ORDER BY loaded_at;` shows both versions.

**Exercise 2: add a rule and prove it.** Add `BAT-013`, a `custom` rule with `columns: [so]`, `expression: so <= ab + bb`, `action: quarantine`, to the silver batting contract and bump its version. Edit `batting.csv`: on the line starting `P020,2024,T04,` change the last three numbers from `68,53,19` to `68,999,19`, and replace the file in the Volume. Run `steps` = `all`. Expected: 42 rules compiled, silver batting 84 in, 1 deduped, **31** rejected, **52** out; gold `fact_batting` has 52 rows; and:

```sql
SELECT rule_ids, payload FROM mlb_dev.governance.dq_quarantine
WHERE run_id = '<your run id>' AND rule_ids LIKE '%BAT-013%';
```
returns your row, exactly as you changed it. Then predict what happens if `so` were blank instead of 999 (BAT-003, not BAT-013: an unknown value is not counted as a violation by business rules, so the missing value is reported once, by the not-null rule).

**Reset after each exercise.** Restore the original contract and `batting.csv` and run once more.

### Part C: classify changes before you make them

The version number is the contract's promise to its consumers.

| Change | Consumers affected? | Version bump |
| --- | --- | --- |
| Tighten a rule (warn to quarantine) | Fewer rows reach them, but no promise is weakened | Minor |
| Add a rule or add a column | No | Minor |
| Fix a typo in a description | No | Patch |
| Remove or rename a column or measure | Yes: anything that selects it breaks | **Major** |
| Change a metric formula | Yes: the number changes | **Major** |
| Weaken a promise (freshness 24 h to 72 h) | Yes: something relying on 24 h can break | **Major** |

The tool `contract_tool.py diff --git-ref main` applies exactly these rules between a branch and `main`, and fails if a breaking change has no major bump. It needs the contracts under Git; the Manual Edition's labs 6 and 7 walk through it.

## Lab 8: plan the move to full automation

**Goal.** List what you still do by hand, decide what to automate first, and know what each step needs. Nothing here needs to run today; it is the plan you will execute in your new role.

**What you did by hand, and its automated equivalent**

| By hand today | Automated equivalent | What it needs |
| --- | --- | --- |
| Upload CSV files into the landing Volume | A scheduled export or ingestion from the source system; later Auto Loader | Access to the source; an ingestion design |
| Edit contracts on your computer, upload the YAML | Contracts live in Git; a merge copies them to the Volume, or the Job reads them from a Databricks Git folder | A repository, a Git credential in the workspace |
| Run lint, compare, diff by hand | A GitHub workflow on every pull request | A workflow file and the repository |
| Build and upload `lakehouse.zip` | A workflow builds it on merge and copies it to the code Volume (later: a Python wheel) | A CLI step with a token |
| Create the Job in the UI | The Job defined as code and deployed | A bundle definition |
| Click Run now | A schedule or a file-arrival trigger | Already in the Job |
| Read the log and queries | A failure notification and a dashboard on the governance tables | Alert setup |

**The Job as code.** A Python script task is called a `spark_python_task` in the API and in bundle files. A starting point (not tested):

```yaml
resources:
  jobs:
    fbl_pipeline:
      name: fbl-pipeline-${bundle.target}
      max_concurrent_runs: 1
      parameters:
        - { name: contracts_dir, default: /Volumes/${var.catalog}/governance/pipeline/contracts }
        - { name: steps,   default: all }
        - { name: stages,  default: all }
        - { name: entities, default: all }
        - { name: plan_only, default: "false" }
        - { name: fail_on_rejects, default: "true" }
      tasks:
        - task_key: run_pipeline
          spark_python_task:
            python_file: /Volumes/${var.catalog}/governance/pipeline/run_pipeline.py
            parameters: ["--catalog", "${var.catalog}",
                         "--pipeline-root", "/Volumes/${var.catalog}/governance/pipeline",
                         "--data-root", "/Volumes/${var.catalog}/bronze/landing",
                         "--run-id", "{{job.run_id}}",
                         "--contracts-dir", "{{job.parameters.contracts_dir}}",
                         "--steps", "{{job.parameters.steps}}", "--stages", "{{job.parameters.stages}}",
                         "--entities", "{{job.parameters.entities}}",
                         "--plan-only", "{{job.parameters.plan_only}}",
                         "--fail-on-rejects", "{{job.parameters.fail_on_rejects}}"]
```

**A sensible order to automate in**

1. **Put the project in a Git repository.** Everything else builds on it. Contracts and transforms become reviewed files.
2. **Run the contract checks on every pull request** (lint, the breaking-change gate). These need no Databricks access, so they are the safest first automation. The project's `contracts.yml` workflow does this; its final publish step was written for the older notebook path, which copied a JSON bundle, so adapt that step to copy the YAML folder to the Volume.
3. **Build and publish `lakehouse.zip` on merge.**
4. **Deploy the Job as code**, with a staging target that runs against a staging catalog first.
5. **Add the schedule and notifications.**
6. **Replace the manual file upload** with whatever the source system allows.

Steps 1 and 2 give you most of the safety and none of the risk, so do them first.
